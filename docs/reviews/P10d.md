## Play button: is Pedro's symptom fixed?

Before: the button read `pos.playing`, the heard position, which reaches the screen through `Tone.Draw` a lookahead plus the 50 ms start offset after the tap, and which the Draw callbacks of a stopped run could set back to playing after Stop. After: the button reads `running`, set synchronously by `play()` and `stop()` through `onRunning`; positions and DROP phases of an ended run are dropped by the `run` counter.

Every path I could find that makes the button show Play while the transport runs:

| Path | Before | After |
|---|---|---|
| First tap, audio context starting (`starting` dims the button while `init` runs) | After init, Play un-dimmed while the transport runs, until the first position is drawn: 6 to 7 frames headless, 165 ms at 6x CPU throttle; longer on a phone if Draw drops callbacks older than its 0.25 s expiry | Stop the frame after init; never Play while running |
| Second tap during init | Button disabled | Same |
| Second tap within 50 ms of Play (`engine.playing` is still false: `Transport.state` reads at `now()`, the start is at `now() + 0.05`) | `play()` again, harmless | Same (see M1) |
| Start promise resolving after a state update | Only `starting` changes after the await | `running` is set inside `play()`, after the await |
| Visibility change, wake lock | Do not touch the transport or the button | Same |
| Audio interruption (OS suspends the context) | Draw stops, position frozen | The transport stays "started", the button stays Stop, which is the transport's state |
| Play tab remount, Simple/Advanced switch, tab switch | The button lives in `App`, not in the tab; it does not remount | Same; `useState(() => engine.playing)` only at App mount |
| DROP or Morph tap | Neither emits `playing: false` | Same |
| `loadSong`/`switchSection` emitting `{...this.pos}` before the first drawn position | `playing: false` for a frame | Does not reach the button |
| Something other than `play()`/`stop()` starting or stopping the transport | None (`grep`: only `index.ts:467` and `477`) | Same |

Headless probe (real app, `/usr/bin/google-chrome`, every animation frame recorded from before the tap, 12 scenarios, each on the old and the new build): first tap with and without the autoplay flag, a picker tile, double taps 30 and 120 ms apart, a tap followed at once by Advanced, Mix, Play and Simple, Stop then Play 200 ms later, Stop and Play 100 ms apart during a Simple drop's build, Morph on and a drop in Advanced then Stop and Play 50 ms apart, a triple tap, Stop alone, a vibe arrow plus a hidden and visible event. Old: the first-tap lag in every scenario (1 to 10 frames Play while running), Stop shown while stopped after Stop in the drop scenarios. New: 0 frames Play while running in all 12; 3 to 8 frames Stop while the transport is still in its 50 ms start window (the button leads the transport, as intended).

**My read.** Pedro's exact sequence (Stop shown, then Play again, while the music plays) did not reproduce headless on the old build either, so neither the builder nor I have seen it. What did reproduce is the button lagging Play after the transport starts (worst on a first tap, after the button un-dims from `starting`: on a phone that is "flickers, then shows Play while the music plays", for as long as the first drawn position takes) and the button stuck on Stop after a Stop (the same bug seen from the other side). The fix is structural, not a patch on one race: the button no longer reads the position stream at all, and I found no remaining path that can show Play while the transport runs. If Pedro's report describes a different mechanism, it is not in the button's state; the one thing the new build still shows on a first tap is the button dimmed for the length of `init` (about 1.1 s at 6x throttle), which Pedro could read as a flicker. That is the intended "starting" state, not a bug, but worth naming when Pedro checks the build.

## Findings

### Errors

### Should-fix

### Minor

**M1. The tap decides on the transport, the button shows `running`.** `src/ui/App.tsx` 299-305.
- `togglePlay` reads `engine.playing`, which is false for 50 ms after `play()` (the transport starts at `now() + 0.05` and `Transport.state` reads at `now()`); the button already shows Stop. A Stop tap in that window calls `play()` again and is lost. Measured in my triple-tap probe; one tap in 50 ms is rare by thumb.
- **Fix:** let the tap read the same state the button shows (an engine getter for the last Play/Stop, or the `running` state), so the button and the tap never disagree.

**M2. `sample_play` starts judging when the transport reaches the asked state.** `tools/shots.py` 435-447.
- Frames between the tap and the transport's start (the `init` on a first tap, then 50 ms) are not judged, so a Stop, Play, Stop flicker there would pass. Pedro's symptom needs the transport running, so it is covered; my probe found no such flicker on HEAD. Sampling also starts only after `page.click` returns and the evaluate round trip.
- **Fix:** also fail if, after the first frame that shows the asked word, any later frame shows the other.

**M3. In Advanced the strip now changes height between Play and the other tabs.** `src/style.css` 411-413, spec 8.6 lines 248 and 262.
- At 700 px of height and up the Play tab's strip is 64 px, the other tabs' 52 px, so in Advanced the strip's top moves 12 px when leaving Play (Simple already did this). Spec line 248 still says the strip is "in the same place on every tab", and line 262 calls the strip "the taller one ... (52 px under 700 px of height)" where line 259 says it is not taller there.
- **Fix:** one sentence in 8.6 saying the Play tab's strip is taller in both modes (its bottom edge stays put), and "(not taller under 700 px of height)" in line 262. Pedro's eye decides whether the 12 px move matters.

## Verdict

**Pass.** 0 errors, 0 should-fix, 3 minor. Both bugs reproduced on `315e17a` are fixed and tested (tests fail on the old code, pass on HEAD); DROP and Morph keep one top edge in Simple and Advanced and across visits at seven sizes, the band is gone, nothing under 48 px. Pedro's exact sequence was not reproduced on either build; the fix removes the only mechanism by which the button could show Play while the transport runs, so his ear and thumb confirm it on the phone.
