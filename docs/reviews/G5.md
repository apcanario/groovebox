## The memory ruling

Measured here, not taken from the builder's report. Four ten-minute runs plus heap-snapshot diffs:

| Run | JS heap, min 1 to 10 | Renderer low points | All Chrome low points |
|---|---|---|---|
| HEAD, take (`npm run record-test`) | +7.6 MB | +26.7 MB | +30.2 MB |
| HEAD with the E1 fix, take | +0.2 MB | +25.8 MB | +37.0 MB |
| HEAD with the E1 fix, no take (`--baseline`) | +0.7 MB | +5.7 MB | +5.9 MB |
| HEAD with the E1 fix, take, Chrome profile on disk | +0.7 MB | +9.8 MB | +10.0 MB: **LONG TAKE PASSED** |

HEAD without a take: JS heap +4.1 MB in four minutes, the same rate as with a take (about 0.9 MB a minute).

Findings:

1. **The JS heap growth is an engine leak, pre-existing, not the recorder.** Heap-snapshot diff over 90 s of plain playback (dev build, default song): +367 `OscillatorNode` (native and wrapper, 4.1 a second), +734 `AudioParam` (their frequency and detune) with their `AutomationEventList`s, Sets and WeakMaps; no `ToneOscillatorNode` left over. The same diff while recording shows exactly the same objects at the same rate and nothing else. Cause: Tone 15.1.22 `Oscillator._start` (`node_modules/tone/build/esm/source/oscillator/Oscillator.js:64-82`) makes a new native oscillator per note and connects `this.frequency` and `this.detune` to its params; the ended node's `dispose()` never disconnects those signals, so every ended oscillator stays reachable from the instrument's frequency signal. Every `Tone.Oscillator` start leaks (MembraneSynth kick, every Synth, PolySynth and fat-oscillator voice), not only drums and Layer 2: the default song happens to start about four a second. A busier song (arp at sixteenths, chords, fat waves) leaks several times faster. The builder's diagnosis of the heap growth is right in substance.
2. **The process-memory growth that fails `record-test` is not that leak.** It survives the E1 fix (+25.8 / +37.0 MB) and is absent without a take (+5.7 MB). The encoder worker's own heap is flat (1.6 to 3.5 MB after forced collections, five minutes sampled over CDP). It is the test harness: Playwright's `browser.new_page()` opens an off-the-record context, where Chrome keeps the origin-private file system in memory, so the MP3 being written to OPFS sits in RAM. With an on-disk profile (`launch_persistent_context`) the same build passes: +0.7 / +9.8 / +10.0 MB. The builder's attribution of this part is wrong, and the changelog repeats it.
3. **Verdict on "memory use flat":** not met at HEAD. With the E1 fix and S2, it is met and measured: the recorder itself holds nothing. The leak is an **error**, not a carry: the row cannot be called done while its own Done-when line is false and its own test fails, the spec's reason for streaming the MP3 is long jams, and the leak grows without bound for as long as the song plays (about 50 MB of JS heap an hour on the default song, more on a busy one, on a phone).

## Findings

### Errors

**E1. Every started oscillator leaks: "memory use flat" is false.** `src/engine/audio.ts:23` (module top, before `const RAMP`). Fix in the engine, once, after the imports: disconnect the oscillator's frequency and detune signals from each native oscillator when it ends. Verified in a scratch copy: JS heap +0.2 MB over the ten-minute take (was +7.6 MB), no `OscillatorNode` growth in the snapshot diff, 151 tests and `smoke` pass. It changes no level and no sound default.

```ts
// Tone 15.1.22 leak: Oscillator._start connects its frequency and detune signals to each new native
// oscillator and never disconnects them, so every ended oscillator stays reachable. Disconnect on end.
{
  const proto = Tone.Oscillator.prototype as unknown as { _start(t: unknown): void; _oscillator: { onended: (n: unknown) => void; frequency: unknown; detune: unknown }; frequency: Tone.Signal<"frequency">; detune: Tone.Signal<"cents"> };
  const start = proto._start;
  proto._start = function (this: typeof proto, t: unknown): void {
    start.call(this, t);
    const node = this._oscillator;
    const end = node.onended;
    node.onended = (n: unknown): void => {
      this.frequency.disconnect(node.frequency as Tone.InputNode);
      this.detune.disconnect(node.detune as Tone.InputNode);
      end(n);
    };
  };
}
```

Add a smoke or record-test check that fails on the leak, such as the JS heap limit already in `record_long.py` (it passes at +0.2 MB with the fix), and a comment naming the Tone version so the patch is dropped when Tone fixes it.

### Should-fix

**S1. A failing encoder leaves the take stuck in "finishing" for good.** `src/engine/mp3.worker.ts:84-92`, `src/engine/recorder.ts:109`, `src/engine/index.ts:279`. An error inside the worker's async `finish()` (OPFS `flush`, `close` or `getFile` throwing, a full disk) is an unhandled rejection in the worker, not a `Worker.onerror`, so `recorder.stop()` never settles: the record button stays disabled, `Keeper.idle()` stays false so no song can be opened, made or deleted until a reload, and the take's log is never saved. When the worker does error, `finishTake` rethrows out of a `void` call (unhandled rejection) and the user is told nothing. Fix: wrap the worker's `finish()` and `onPort` work in try/catch and post `{ type: "error", message }`; reject on it in `Recorder`; add a timeout (say 10 s after `stop`) that rejects; in `finishTake` catch, still save the log and reset the state (it does, in `finally`), and emit a failed take so `App` shows an error line.

**S2. `record-test` measures the harness, not the app.** `tools/record_long.py:74-77`. `browser.new_page()` is an off-the-record context, where OPFS lives in memory, so the MP3 under test counts as memory growth (about its own size, plus the in-memory file system's overhead). The phone writes OPFS to disk. Fix: launch with `p.chromium.launch_persistent_context(tempfile.mkdtemp(), args=..., viewport={"width": 390, "height": 844}, accept_downloads=True)`, take the page from it and the CDP session from `context.new_cdp_session(page)`; remove the temp profile afterwards. With that and E1, the test passes here (+0.7 / +9.8 / +10.0 MB). Also make `--baseline` report the same low-point figures as a take (`:115-119` prints end minus start), so the two can be compared, which the changelog line tried to do.

### Minor

**M1. Changelog memory line is wrong in part.** `docs/CHANGELOG.md:7`. It attributes all growth to the leak "about 2 a second each for drums and Layer 2" and says the recorder adds nothing. The heap growth is the leak, from every oscillator start, not two instruments; the process growth is the test's in-memory OPFS (S2). Fix when the chat finalises the line: report the post-fix numbers and name the cause as above.

**M2. Refused and no-op edits are logged.** `src/engine/index.ts:331-571`: `note()` runs before the call, so a refused `deleteSection`, `setChords`, `copySection` and an unchanged `bpm` are logged. Harmless on replay (refused again), but the log is not what happened. Fix: log after `ok`, or record the choice in the changelog.

**M3. Play during the Stop tail records the new run into the old take.** `src/engine/index.ts:184-190` with `:206-211`. Tapping Play within 1.5 s of Stop restarts the music while the state is `finishing`; the take keeps capturing until the timer fires and ends mid-phrase. Fix: in `play()`, if the state is `finishing`, call `finishTake()` first.

**M4. The take sheet rebuilds its File on every render.** `src/ui/App.tsx:88-89`. `App` re-renders on every position change; `new File(...)` and `navigator.canShare` run each time. Fix: `useMemo` on `take`.

**M5. Two copies of the song-name rule.** `src/engine/index.ts:480-487` duplicates `cleanName` in `src/store/library.ts:51`. Fix: move `cleanName` and `MAX_SONG_NAME` to `src/engine/song.ts` and use it in both.

**M6. Keeper and the record state machine have no unit tests.** `src/store/keeper.ts`, `src/engine/index.ts:220-232`. Smoke covers them end to end only. Fix: vitest for the Keeper with a fake engine and `MemoryKv` (saves the log only when it changed, open/create/remove refused while not idle, deleting the open song opens the next); test `record()` transitions off, armed, off and armed to recording on `play()` with the take start stubbed.

**M7. The LGPL notice does not ship.** `dist/assets/mp3.worker-*.js` holds no licence text. LGPL-3.0 asks for a notice and the licence with the distributed work. Fix: add `public/LICENSES.txt` naming `@breezystack/lamejs`, LGPL-3.0, its source URL and that it is used unmodified in its own worker chunk; the APK (G6) ships it too.

**M8. A capture processor that fails to load is silent.** `src/engine/index.ts:138` swallows the `prepareTap` error, and `startTake` (`:250`) then turns the state back to off with no message: the Record button seems dead. Fix: keep the error and expose it (a `recordAvailable` flag or an error through `onTake`), and have the transport show it.

## Verdict

**fix.** 1 error, 2 should-fix, 8 minor. The save, record, log and MP3 work is sound and the recorder itself keeps memory flat; the row is not done until the engine's oscillator leak is fixed (E1) and `record-test` measures with storage on disk (S2) and passes.
