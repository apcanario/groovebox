## Known deviation: no Vitest

Vitest could not be installed (the permission system refused it), so `tests/harness.ts` is a dependency-free runner with Vitest-shaped calls, run under Node 22's native type stripping. **The tests are real.** I copied the tree to /tmp and broke the code four ways: toggle cancel removed, switches applied mid-bar, lead seed ignored, one chord degree wrong. Each break failed between 1 and 4 tests, and the runner exits non-zero, so `check` stops. For the row's logic the coverage is adequate. The weak points are in the harness itself: `deepEqual` compares `JSON.stringify` output, so NaN equals null, `undefined` fields vanish and key order matters; async tests are not supported. Graded should-fix (finding S6), not error.

## Findings

### Errors

None.

### Should-fix

**S1. Stop can leave a pad, a sustained chord or a long bass note ringing for seconds.** `src/engine/index.ts:85-94` (line 91).
The transport callback runs about 0.1 s (lookAhead) before each step. `PolySynth` holds a future attack in a `context.setTimeout` and does not add it to `_activeVoices` until its time comes. `releaseAll(now)` therefore misses any note scheduled in that window. Press Stop just before a chord start and the pad (`len` = rest of the chord, up to 32 steps, about 4 s at 122 bpm, then a 1.8 s release) or the sustained synth plays out in full after Stop. `MonoSynth` bass notes (`long`, up to 7.5 steps) behave the same way, because the release at `now` comes before the future attack.
Fix: in `stop()`, release again once the lookahead has passed, for example `Tone.getContext().setTimeout(() => releaseAll(Tone.now()), Tone.getContext().lookAhead + 0.02)` for every instrument. Alternatively, set a `stopped` flag that `Poly.trigger` and `Bass.trigger` check. Add a smoke check: stop right after a bar line, wait 1 s, and confirm that no new attacks happen (meter or a trigger counter).

**S2. Changing the wave mid-note is a step: a click.** `src/engine/audio.ts:208-210` (Bass) and `248-250` (Poly).
`set({ oscillator: { type } })` makes Tone's OmniOscillator replace its source oscillator at once while voices sound. That is a waveform discontinuity, against spec 5 ("every knob is safe to move while playing: no clicks") and spec 7 ("never stepped"). The test screen does not expose the wave yet, but the engine API (`setParam(inst, "wave", …)`) does, and G3 will use it.
Fix: apply the new wave to voices at their next attack only. Keep the wave in the instrument and set it on the idle voice just before `triggerAttackRelease`, or crossfade two voice sets through a 30 ms gain ramp. Document which approach was taken.

**S3. Swing is applied to drums only, so bass and synth flam against the swung hats.** `src/engine/sequencer.ts:170` (only the drum events get `shift`); `176`, `186`, `226`, `238` (no shift).
The default Outro plays `houseShuffle` (swing 0.18) with the `rolling` bass, which hits odd sixteenths 1, 3, 5 and so on. The hats land about 22 ms late and the bass lands straight. The Break and Outro stabs on steps 3 and 11 are unswung in the same way.
Fix: add `shift` to every `NoteEvent` and use the section's drum-pattern swing for odd steps across all instruments. Apply it in `Engine.tick` (`index.ts:183-202`) for bass, synth and layers. Add a unit test: in a swung section, every event on an odd step carries the same shift.

**S4. Layer 1 polyphony is 6, too few for pad mode.** `src/engine/audio.ts:304` (`layer1: new Poly(buses, 2, 6, 0.5)`; layer 2 has 12).
Either layer can be a pad (spec 3). A 4-note pad with release overlapping the next chord's 4 notes needs 8 voices, so Tone drops notes at every chord change when Layer 1 is a pad.
Fix: give both layers the same cap, sized for the worst mode: 4 pad notes times 2 overlapping chords is 8, so 8 to 10.

**S5. Controls smaller than 48 px on the test screen.** `src/style.css:235-238` (`.slider input` is 40 px tall, with the browser's default thumb of about 16 px), and `src/main.ts:78-80` with `src/style.css:270` (the `fast · balanced · safe` hint links are 13 px inline text).
CLAUDE.md requires every control to be at least 48 px.
Fix: make the range input at least 48 px tall and style its thumb to at least 48 px. Render the three buffer links as buttons of at least 48 px in a row (or a 3-way segmented control).

**S6. The test runner is not Vitest (known deviation).** `tests/harness.ts:32-34`, `package.json:12`.
The row asks for Vitest. The substitute is real and adequate (see above), but it is weaker in places.
Fix:
- Replace `deepEqual` with a structural recursive compare (`Object.is` on leaves, arrays by index, objects by sorted keys).
- Record the deviation under Choices in the changelog.
- Add a Carried item: "swap tests/harness.ts for Vitest when the install is allowed (import line change only)".
- Add `"engines": { "node": ">=22.18" }` to `package.json`, because `node tests/run.ts` depends on native type stripping.

**S7. Up to six 4x-oversampled waveshapers run all the time on the phone CPU.** `src/engine/audio.ts:44` (drive on bass, synth, layer1, layer2), `127` (kick), `314` (master saturation).
`Tone.Distortion` with `wet: 0` still runs its 4x-oversampled WaveShaper. Buffer underruns are on C1's own list of crackle causes, and spec 4 makes phone CPU the budget, so all this oversampling can cause the crackle it was meant to fix.
Fix: keep 4x on the kick drive and the master saturation. Use `"2x"` on the per-channel drives. Disconnect a drive from the chain, routing around it through a dry path, while its amount is 0: crossfade with a 30 ms ramp, then disconnect.

### Minor

**M1. `setParam` and `apply` do not clamp to `PATCH_RANGES`.** `src/engine/index.ts:97-101`, `src/engine/audio.ts:163`. An out-of-range value goes into the song and into Tone (for example attack 0). Fix: clamp numeric values to `PATCH_RANGES[key]` in `Engine.setParam` before storing them, and ignore unknown waves.

**M2. `loadSong` does not validate.** `src/engine/index.ts:69-76`. Fix: run `validateSong` and throw (or refuse) on errors. G5 will feed it documents from IndexedDB.

**M3. The UI's section index can differ from the scheduler's in the lookahead window.** `src/main.ts:165`, `src/engine/index.ts:115-117`. The UI passes `position().section`, which is drawn when the sound plays. The scheduler's `current` changes about 0.1 s earlier at a section switch. A toggle tapped in that window flips the old section at once and silently. Fix: add `Engine.toggleInstrumentInPlaying(inst)`, which uses the scheduler's section, or have `toggleInstrument` treat the section that is about to play as the playing one.

**M4. A 4 ms pump ramp at depth 0.6 is still close to a step on held bass and pads.** `src/engine/audio.ts:337`. The kick may mask it; if not, it ticks. Fix: lengthen the duck ramp to 8–10 ms. Pedro judges by ear.

**M5. Resonance at the cap adds about 10 dB** (measured above). `src/engine/audio.ts:16, 43`. Q 8 on a -24 dB filter (two cascaded biquads, each at Q 8) gives a very steep peak, and the drive comes after it. The mix stays under the limiter, but this is the C1 area. Fix: either compensate the level as Q rises (for example `level × 1/(1 + 0.15·(Q-0.7))`) or set `MAX_Q` to 5–6 for the `-24` filters. Record the choice.

**M6. The smoke test's "too hot" check reads a smoothed RMS meter, which cannot see peaks or clipping.** `tools/smoke.py:617-627`, `src/engine/audio.ts:315, 362-365`. Fix: add a peak reading, from an `AnalyserNode` after the limiter holding the maximum absolute sample over the window. Fail if the peak is ≥ 0 dBFS, or report it.

**M7. Edited drum grids are 16 steps; spec 3 says the drum sequencer has 8 steps per bar.** `src/engine/song.ts:88-92, 271`. Storing 16 steps keeps the presets' sixteenth hats and is the more reasonable reading. Fix: record it under Choices in the changelog ("grid stored at 16 steps; the 8-step editor of G3 edits the even steps"), so G3 does not reopen it.

**M8. Some logic has no tests.** `src/engine/song.ts:311-313` (`sectionDrumGrid` with an edited grid); `src/music/scales.ts:83-88` (`scaleNotesInRange`, unused); `chordAt` with half-bar chords. There is no test that a song round-tripped through `serializeSong`/`parseSong` plays the same events, which is spec 3's "a saved jam reloads note for note". Fix: add these tests, or delete `scaleNotesInRange` if nothing will use it.

**M9. `render()` deep-clones the whole song on every sixteenth.** `src/main.ts:89` (`engine.getSong()` is a JSON round-trip). That is avoidable garbage on the phone. Fix: add a cheap `engine.sectionOn(i)` or read-only accessor, or render only when pending or section state changes.

**M10. C1 cannot be closed by this row.** `docs/BACKLOG.md` Carried C1, and `docs/CHANGELOG.md`. The C1 changes are listed only in the commit message and the `audio.ts:5-8` header:
- every waveshaper at 4x
- Q capped 14 → 8
- synth filters top out at 10 kHz
- hat trim 0.4 → 0.22, hat highpass 8.5 → 7.5 kHz, clap trim 0.9 → 0.6
- master 0.7 → 0.5
- limiter release 10 → 120 ms
- pump ramped
- default buffer `balanced`

Fix (at row close): list these in the changelog line as C1 requires. Keep C1 in Carried, reworded as "fixes applied in G1, waiting for Pedro's ear", because C1 says "Pedro confirms by ear". Add a Listen-for item about treble crackle.

## C1 handling

Every check in C1's list was addressed in order: drive oversampling, resonance cap and band limit, hat and clap levels, limiter drive and release, buffer default. The work is sound. Two cautions remain: S7 (CPU cost of the oversampling, an underrun risk in its own right) and M5/M6 (resonance peak, no peak metering). Whether the crackle is gone only Pedro's ears can say.
